# Módulo 2: Keycloak y los protocolos estandarizados de autenticación

## 1. Descripción

En una arquitectura de software moderna orientada a servicios o microservicios, la seguridad no puede depender de soluciones propietarias o mecanismos caseros de validación de credenciales. La reutilización y la interoperabilidad exigen el uso de estándares abiertos. Keycloak actúa como un motor agnóstico de protocolos de identidad e implementa de forma nativa especificaciones globales avaladas por la *Internet Engineering Task Force* (IETF) y la *OpenID Foundation*.

Para comprender cómo Keycloak gobierna la seguridad, es vital distinguir con precisión los tres protocolos principales que soporta: **OAuth 2.0** (framework de autorización delegada), **OpenID Connect (OIDC)** (capa de identidad construida sobre OAuth 2.0) y **SAML 2.0** (protocolo basado en XML, tradicionalmente orientado a entornos corporativos y heredados).

## 2. Objetivos

- Diferenciar conceptual y técnicamente entre **autenticación** y **autorización**.
- Analizar el funcionamiento interno y los casos de uso idóneos para **OAuth 2.0**, **OpenID Connect (OIDC)** y **SAML 2.0** dentro de Keycloak.
- Ejecutar un caso práctico mediante la API de Keycloak utilizando `cURL` para solicitar y analizar un token bajo un flujo estándar.
- Identificar los **tres tipos de tokens** que emite Keycloak en un flujo OIDC completo y cuándo usar cada uno.

## 3. Desarrollo del tema y casos prácticos

### Diferencia fundamental: autenticación vs. autorización

Es común utilizar ambos términos de manera indistinta, pero en IAM representan procesos completamente diferentes:

1. **Autenticación (*Authentication* — ¿quién eres?):** proceso mediante el cual Keycloak verifica la identidad de un usuario; por ejemplo, mediante credenciales en un formulario de inicio de sesión, un factor MFA o biometría. Su estándar por excelencia en la web moderna es **OpenID Connect (OIDC)**.
2. **Autorización (*Authorization* — ¿qué puedes hacer?):** proceso mediante el cual se determina si un usuario o una aplicación autenticada tiene los permisos necesarios para acceder a un recurso protegido o ejecutar una acción. Su estándar global es **OAuth 2.0**.

> **Precisión técnica importante:** OAuth 2.0 **no es un protocolo de autenticación**. Es un *framework* de autorización delegada que permite a una aplicación obtener acceso limitado a un recurso en nombre de un usuario, sin conocer sus credenciales. OIDC **extiende OAuth 2.0** añadiendo la capa de identidad que OAuth 2.0 deliberadamente omite.

### Análisis de los protocolos soportados en Keycloak

#### 1. OAuth 2.0: framework de autorización delegada

OAuth 2.0 **no es un protocolo de autenticación**, sino un marco de autorización. Permite que una aplicación de terceros obtenga acceso limitado a un servicio HTTP (API) en nombre de un propietario de recursos (el usuario), o mediante la identidad de la propia aplicación, sin exponer las credenciales del usuario.

- **Tokens asociados:** emite principalmente *Access Tokens* (opacos o en formato JWT).
- **Casos de uso en Keycloak:** protección de APIs REST y comunicación *Machine-to-Machine* (backend a backend).
- **Flujos principales:** Authorization Code (con PKCE para SPAs), Client Credentials y Refresh Token.

#### 2. OpenID Connect (OIDC): capa de identidad sobre OAuth 2.0

OIDC es una extensión de identidad construida directamente **sobre OAuth 2.0**. Mientras OAuth 2.0 permite que una aplicación tenga permiso para llamar a una API, OIDC añade la capacidad de verificar la identidad del usuario y obtener información básica sobre su perfil mediante un documento estructurado llamado **ID Token**.

- **Tokens asociados:** emite un *ID Token* (para autenticación y perfil) y un *Access Token* (para autorización ante APIs). En flujos con renovación, también puede emitir un *Refresh Token*.
- **Casos de uso en Keycloak:** inicio de sesión en aplicaciones web modernas, portales corporativos y aplicaciones móviles o *Single Page Applications* (SPA).

> **Nota crítica:** OIDC solo aplica cuando hay un usuario involucrado. En flujos *machine-to-machine* (como `client_credentials`), no hay una identidad de usuario que autenticar y, por lo tanto, **no se emite un ID Token**. El scope `openid` no tiene efecto en estos flujos.

#### 3. SAML 2.0: Security Assertion Markup Language

SAML 2.0 es un estándar maduro y robusto basado en **XML**, diseñado principalmente para escenarios de *Single Sign-On* (SSO) entre dominios empresariales. En lugar de emitir tokens JSON ligeros (JWT), SAML intercambia documentos XML firmados digitalmente, conocidos como *assertions* (aserciones), entre el proveedor de identidad (Keycloak) y el proveedor de servicio (la aplicación).

- **Casos de uso en Keycloak:** integración con software corporativo heredado (*legacy*) y plataformas empresariales como Salesforce, SAP o ServiceNow.

### Los tres tokens de OIDC: guía de referencia

Cuando se ejecuta un flujo OIDC completo (con usuario), Keycloak puede devolver **tres tipos de tokens**. Confundirlos es uno de los errores más comunes en desarrollo:

| Característica | Access Token | ID Token | Refresh Token |
|---|---|---|---|
| **Propósito** | Autorizar llamadas a APIs | Probar la identidad del usuario | Renovar el access token |
| **Firma** | RS256 (asimétrica) | RS256 (asimétrica) | HS512 (simétrica, interna del realm) |
| **Audiencia (`aud`)** | El servidor de recursos (API) | El cliente (frontend) | El realm de Keycloak |
| **Destinatario** | Tu API | Tu frontend (nunca el backend) | Solo Keycloak (endpoint de tokens) |
| **Tiempo de vida típico** | 300 s (5 min) | 300 s (5 min) | 1800 s (30 min) |
| **¿Es legible por el cliente?** | Sí (JWT decodificable) | Sí (JWT decodificable) | No (tratar como opaco) |

> **Error común:** enviar el **ID Token** a una API como si fuera un Access Token. La API puede rechazarlo porque su claim `aud` no coincide. El ID Token es exclusivamente para el frontend, para confirmar que el inicio de sesión ocurrió.

### Caso práctico: solicitud de tokens vía cURL (Client Credentials Grant)

Para ilustrar cómo Keycloak procesa solicitudes bajo estos estándares, simularemos una petición de autorización con *Client Credentials*. Este flujo se utiliza cuando una aplicación o microservicio cliente se autentica directamente ante Keycloak para obtener un *Access Token*, sin la intervención de un usuario interactivo.

```bash
curl -X POST 'http://localhost:8080/realms/myrealm/protocol/openid-connect/token' \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -u "my-client:<client-secret>" \
  -d "grant_type=client_credentials"
```

> **Nota sobre `scope`:** En `client_credentials` no se debe incluir `scope=openid`. Este flujo es puramente OAuth 2.0 (*machine-to-machine*, sin usuario) y no emite un ID Token. Si se necesita limitar el acceso, se pueden solicitar scopes funcionales (por ejemplo, `scope=profile` o scopes personalizados del servidor de recursos).

#### Desglose línea por línea de la petición

- `-X POST`: método HTTP utilizado para solicitar o intercambiar credenciales en el endpoint de tokens de Keycloak.
- `http://localhost:8080/realms/myrealm/protocol/openid-connect/token`: endpoint específico dentro del realm `myrealm`, encargado de emitir y renovar tokens.
- `-H "Content-Type: application/x-www-form-urlencoded"`: indica que los datos del cuerpo de la petición están codificados como un formulario web estándar (clave-valor).
- `-u "my-client:<client-secret>"`: utiliza autenticación HTTP Basic, recomendada por la especificación OAuth 2.0 para clientes *confidential*. Keycloak también acepta `client_id` y `client_secret` como parámetros del cuerpo (`-d`), pero Basic Auth es la práctica estándar.
- `-d "grant_type=client_credentials"`: especifica el tipo de concesión OAuth 2.0. En este caso, se trata de autenticación máquina a máquina basada en las credenciales del cliente.

#### Estructura esperada de la respuesta JSON

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 300,
  "refresh_expires_in": 0,
  "token_type": "Bearer"
}
```

> **Observación sobre `refresh_expires_in: 0`:** En el flujo `client_credentials` no se emite un Refresh Token. La máquina cliente simplemente solicita un nuevo Access Token cuando el anterior expira. Este comportamiento es correcto y esperado.

- `access_token`: credencial digital firmada (JWT) que se adjunta en las cabeceras HTTP (`Authorization: Bearer <token>`) para consumir APIs protegidas.
- `expires_in`: tiempo de vida del Access Token en segundos (por defecto, 300 segundos o 5 minutos en configuraciones estándar de desarrollo).
- `refresh_expires_in`: en `client_credentials`, vale `0` porque no hay Refresh Token. En flujos con usuario (Authorization Code), tendrá un valor mayor que `0`.
- `token_type`: define el esquema de autenticación HTTP; `Bearer` es el estándar de la industria.

#### Advertencia: el claim `aud` del Access Token

Por defecto, Keycloak no incluye el servidor de recursos en el claim `aud` del Access Token. Esto significa que una API que valide correctamente el token (verificando su firma y audiencia) puede rechazarlo, aunque el token sea válido criptográficamente.

Para resolverlo, configura un **Audience Protocol Mapper** en el cliente que emite el token:

1. En la Admin Console, navega a **Clients → [tu-cliente] → Client scopes → [cliente]-dedicated → Configure a new mapper → Audience**.
2. Configura **Included Client Audience** con el nombre del servidor de recursos (API).
3. Activa **Add to access token**.

Sin este paso, el token será válido criptográficamente, pero puede resultar inutilizable para la API.

## 4. Resumen

- Keycloak centraliza la seguridad mediante estándares abiertos, liberando a los desarrolladores de implementar lógica criptográfica y de sesiones propia.
- OAuth 2.0 es un framework de autorización delegada (no un protocolo de autenticación), mientras que OIDC extiende OAuth 2.0 añadiendo la capa de identidad (ID Token).
- SAML 2.0 sigue vigente en entornos corporativos complejos basados en XML y puede coexistir con arquitecturas OIDC/OAuth 2.0 dentro de Keycloak.
- OIDC puede emitir tres tipos de tokens (Access, ID y Refresh) con propósitos, destinatarios y características distintas. Confundirlos es un error frecuente.
- El flujo `client_credentials` es puramente OAuth 2.0, sin usuario; no emite ID Token ni Refresh Token y no debe incluir `scope=openid`.
- El claim `aud` del Access Token debe configurarse explícitamente mediante un Audience Protocol Mapper para que los servidores de recursos lo acepten.

## 5. Preguntas de autoevaluación

### ¿Cuál es la diferencia fundamental entre el propósito de OAuth 2.0 y OpenID Connect (OIDC)?

**Respuesta:** OAuth 2.0 es un framework diseñado para la autorización delegada (acceso a recursos y APIs), mientras que OIDC es una capa de identidad construida sobre OAuth 2.0 y orientada a la autenticación: permite saber quién es el usuario y proporciona un ID Token.

### ¿Qué formato de intercambio de datos utiliza principalmente SAML 2.0 para sus mensajes y aserciones?

**Respuesta:** XML (*Extensible Markup Language*), a diferencia de OIDC/OAuth 2.0, que emplean predominantemente JSON y JWT.

### En el flujo ejecutado mediante cURL, ¿qué significa `grant_type=client_credentials`?

**Respuesta:** Indica que la aplicación cliente se autentica por sí misma (comunicación máquina a máquina o servicio a servicio), sin la interacción directa de un usuario humano.

### ¿Qué tipo de token emite OpenID Connect para certificar la identidad del usuario que ha iniciado sesión?

**Respuesta:** El ID Token, un JSON Web Token que contiene los claims de identidad del usuario.

### ¿En qué escenarios corporativos se recomienda seleccionar SAML 2.0 en lugar de OIDC?

**Respuesta:** En integraciones con sistemas empresariales heredados (*legacy*), software corporativo tradicional (como Salesforce o SAP) o requisitos de cumplimiento normativo que exijan firmas e intercambios basados en XML.

### ¿Qué representa el campo `expires_in` devuelto por el endpoint de tokens de Keycloak?

**Respuesta:** El tiempo de vigencia, en segundos, que le queda al Access Token antes de expirar y requerir una renovación mediante un Refresh Token o una nueva autenticación.

### ¿Por qué el flujo `client_credentials` no emite un ID Token ni un Refresh Token?

**Respuesta:** Porque es un flujo puramente OAuth 2.0, sin intervención de usuario. No hay identidad de usuario que autenticar (por eso no se emite ID Token) y la máquina cliente puede solicitar nuevos Access Tokens cuando los necesite (por eso no se emite Refresh Token).

### ¿Qué configuración es necesaria para que una API acepte un Access Token emitido por Keycloak?

**Respuesta:** El token debe incluir el servidor de recursos en su claim `aud`. Esto se logra configurando un Audience Protocol Mapper en el cliente emisor de tokens. Sin esta configuración, la API puede rechazar el token aunque sea criptográficamente válido.
