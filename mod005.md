# Módulo 5: Administración de usuarios en Keycloak

## 1. Descripción

La administración de usuarios en Keycloak es el proceso central mediante el cual se gestionan las identidades digitales, los ciclos de vida de las cuentas, las credenciales, los atributos personalizados y las asignaciones de acceso dentro de un realm. A diferencia de los sistemas tradicionales, donde cada aplicación almacena y cifra contraseñas en bases de datos dispersas, Keycloak centraliza la base de datos de identidades. Esto contribuye al cumplimiento de normativas de seguridad (como GDPR), a la resistencia frente a ataques de fuerza bruta y a la trazabilidad mediante auditorías unificadas.

Keycloak ofrece dos vías de administración de usuarios: la **Consola de Administración gráfica (Admin UI)**, para operadores e ingenieros de soporte, y la **Interfaz de Línea de Comandos / REST API (`kcadm.sh`)**, para arquitecturas automatizadas, aprovisionamiento masivo (*bulk onboarding*) e integración en pipelines de CI/CD.

> **Versión objetivo:** Este módulo está basado en **Keycloak 26.x**. Los comportamientos descritos sobre User Profile y atributos son específicos de esta serie.

## 2. Objetivos

- Comprender la estructura interna de un objeto usuario en Keycloak (metadatos, credenciales y atributos).
- Gestionar el ciclo de vida completo de un usuario (creación, activación, asignación de credenciales y acciones requeridas) mediante la interfaz gráfica y la CLI.
- Implementar configuraciones avanzadas, como el control de estados de cuenta y la gestión de credenciales temporales o permanentes.
- Entender el rol del **User Profile** en Keycloak 26 y su impacto en la creación y validación de usuarios.

## 3. Desarrollo del tema y casos prácticos

### Anatomía de un objeto usuario en Keycloak

Un registro de usuario en Keycloak no es una simple tupla de nombre y contraseña; contiene una estructura JSON que comprende:

- **Identificador único universal (UUID):** se genera automáticamente al crear la cuenta. Es la referencia inmutable utilizada en tokens y mapeos de bases de datos.
- **Atributos de identificación básica:** `username` y `email`. Estos campos reciben un tratamiento especial de unicidad e indexación en el motor de persistencia.
- **Credenciales (*credentials*):** almacenes hash seguros de contraseñas, configuraciones TOTP (*Two-Factor Authentication*) o llaves WebAuthn asociadas.
- **Atributos personalizados (*attributes*):** pares clave-valor arbitrarios (por ejemplo, `department: "Engineering"`, `employeeId: "99823"`) que pueden incluirse dinámicamente como *claims* en los tokens JWT.
- **Acciones requeridas (*Required Actions*):** indicadores que fuerzan al usuario a realizar tareas obligatorias en su próximo inicio de sesión (por ejemplo, actualizar la contraseña, verificar el correo electrónico o configurar MFA).

### El User Profile en Keycloak 26: qué cambió y por qué importa

En **Keycloak 26**, el **User Profile** está **habilitado por defecto** y define qué atributos son válidos para los usuarios y qué reglas de validación se aplican. Esto tiene varias implicaciones:

1. **Atributos gestionados y no gestionados:** el User Profile distingue entre atributos **gestionados** (definidos explícitamente en `Realm Settings → User Profile`) y **no gestionados** (otros atributos, ignorados por defecto). Los atributos no gestionados requieren activación explícita en `Realm Settings → General → Unmanaged Attributes`.
2. **`firstName` y `lastName` son obligatorios:** por defecto, el User Profile exige ambos campos. Si intentas crear un usuario solo con `username` y `enabled=true`, recibirás el error `error-user-attribute-required`. Este es uno de los motivos habituales de fallo al automatizar la creación de usuarios con `kcadm.sh`.
3. **Problema conocido en 26.1.0:** hubo un error en esta versión por el que los atributos del User Profile se prefijaban incorrectamente con `profile.attributes.` al guardarlos desde la interfaz, lo que podía causar pérdida de datos en `firstName` y `lastName`. Se recomienda utilizar **Keycloak 26.2 o una versión posterior** para evitar este problema.

> **Recomendación:** Antes de crear usuarios masivamente mediante CLI, verifica la configuración de User Profile en el realm y asegúrate de que los atributos que necesitas estén definidos y no tengan requisitos obligatorios que no estés proporcionando.

### Caso práctico avanzado: gestión automatizada de usuarios vía Admin CLI (`kcadm.sh`)

En entornos empresariales, el alta de usuarios suele delegarse desde sistemas externos (como ERP o portales de recursos humanos) hacia Keycloak mediante scripts o microservicios que consumen su API REST a través de la CLI de administración.

El siguiente procedimiento muestra cómo crear un usuario con atributos, habilitar su cuenta, asignar una contraseña temporal que deba cambiar en el primer inicio de sesión y consultar el UUID generado.

> **Requisito previo:** Este script presupone que ya iniciaste sesión con `kcadm.sh config credentials` (consulta el Módulo 3). Si no lo hiciste, la CLI devolverá un error de autenticación.

```bash
# Paso 1: autenticarse en Keycloak como administrador global
/opt/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080 \
  --realm master \
  --user admin \
  --password admin

# Paso 2: crear un usuario en el realm 'mi-realm'
/opt/keycloak/bin/kcadm.sh create users -r mi-realm \
  -s username="mgarcia" \
  -s email="mgarcia@empresa.com" \
  -s firstName="Mateo" \
  -s lastName="García" \
  -s enabled=true \
  -s emailVerified=false

# Paso 3: obtener dinámicamente el UUID asignado al usuario
USER_UUID=$(/opt/keycloak/bin/kcadm.sh get users -r mi-realm \
  -q exact=true \
  -q username=mgarcia \
  --fields id --format csv --noquotes)
echo "El UUID generado para el usuario es: $USER_UUID"

# Paso 4: añadir atributos personalizados al usuario (requiere el UUID)
/opt/keycloak/bin/kcadm.sh update users/$USER_UUID -r mi-realm \
  -s 'attributes={"department":["Ingeniería de Software"],"costCenter":["CC-4090"]}'

# Paso 5: asignar una contraseña temporal y exigir que se cambie en el primer inicio de sesión
/opt/keycloak/bin/kcadm.sh set-password -r mi-realm \
  --userid "$USER_UUID" \
  --new-password "TempPassword2026!" \
  --temporary

# Paso 6: añadir explícitamente la acción requerida para verificar el correo
/opt/keycloak/bin/kcadm.sh update users/$USER_UUID -r mi-realm \
  -s 'requiredActions=["VERIFY_EMAIL"]'
```

> **Seguridad:** Las credenciales del ejemplo (`admin/admin` y la contraseña temporal) son ilustrativas; no las reutilices. Usa credenciales únicas y almacena los secretos de manera segura, no directamente en scripts compartidos.

#### Desglose técnico línea por línea

##### Paso 2: creación del usuario

- `kcadm.sh create users -r mi-realm ...`: envía una solicitud HTTP POST al endpoint de usuarios del realm objetivo.
- `-s firstName="Mateo"` y `-s lastName="García"`: son obligatorios con la configuración predeterminada de User Profile en Keycloak 26. Omitirlos cuando sean requeridos produce `error-user-attribute-required`.
- `-s emailVerified=false`: indica que el correo electrónico aún no se ha validado. Si el realm exige verificación, se iniciará el flujo correspondiente.

##### Paso 3: obtención del UUID

- `-q exact=true`: es crítico. Sin este parámetro, la búsqueda `username=mgarcia` también podría devolver usuarios como `mgarcia2` o `admin-mgarcia`. El orden importa: `exact=true` debe ir antes de `username=...`.
- `--fields id --format csv --noquotes`: extrae únicamente el UUID en formato limpio para almacenarlo en la variable `USER_UUID`.

##### Paso 4: atributos personalizados

- `-s 'attributes={"department":["Ingeniería de Software"],"costCenter":["CC-4090"]}'`: envía los atributos como un objeto JSON completo, con los valores representados como listas. En Keycloak 26, no se utiliza la notación de punto (`attributes.department=[...]`) para este caso.
- Los atributos personalizados deben estar definidos en el User Profile si se quiere que sean validados. Los atributos no gestionados requieren activación en **Realm Settings → General → Unmanaged Attributes**.

##### Paso 5: contraseña temporal

- `--temporary`: marca la contraseña como provisional. En el siguiente inicio de sesión, Keycloak obliga al usuario a establecer una contraseña personal. Internamente, añade `UPDATE_PASSWORD` a las Required Actions del usuario.

##### Paso 6: Required Actions

- `-s 'requiredActions=["VERIFY_EMAIL"]'`: añade tareas pendientes que el usuario debe completar antes de tener acceso pleno. Algunos valores válidos son `VERIFY_EMAIL`, `UPDATE_PASSWORD`, `CONFIGURE_TOTP`, `UPDATE_PROFILE` y `TERMS_AND_CONDITIONS`.

> **Nota:** `VERIFY_EMAIL` solo funcionará si el realm tiene configurado un servidor SMTP. Sin SMTP, el usuario no podrá completar la verificación del correo.

## 4. Resumen

- La administración de usuarios en Keycloak centraliza la seguridad y evita duplicar credenciales en las aplicaciones cliente.
- Los objetos de usuario contienen metadatos extensibles mediante atributos personalizados y estados de control, como acciones requeridas y contraseñas temporales.
- En Keycloak 26, el User Profile está habilitado por defecto y determina qué atributos son válidos; de forma predeterminada, exige `firstName` y `lastName`.
- Los atributos personalizados se envían como un objeto JSON completo en `kcadm.sh`, no mediante notación de punto.
- La búsqueda por `username` requiere `-q exact=true` para evitar coincidencias parciales.
- La automatización mediante `kcadm.sh` permite integrar el aprovisionamiento de identidades en procesos de infraestructura como código y flujos DevOps.

## 5. Preguntas de autoevaluación

### ¿Qué representa el UUID generado automáticamente al crear un usuario en Keycloak?

**Respuesta:** Es la referencia interna inmutable de la identidad del usuario en el sistema, utilizada por la base de datos, los tokens y las relaciones de mapeo, independientemente de si el nombre de usuario cambia en el futuro.

### ¿Qué efecto produce el modificador `--temporary` al ejecutar `kcadm.sh set-password`?

**Respuesta:** Marca la contraseña asignada como provisional y obliga al usuario a cambiarla la primera vez que se autentique correctamente. Internamente, añade `UPDATE_PASSWORD` a las Required Actions.

### ¿Para qué sirven los atributos personalizados (`attributes`) dentro del perfil de usuario en Keycloak?

**Respuesta:** Para almacenar metadatos adicionales (como departamentos, números de empleado o centros de coste) que pueden mapearse e incluirse en los claims del JWT emitido.

### ¿Cómo permite la Admin CLI consultar el UUID de un usuario mediante una búsqueda exacta por nombre de cuenta (`username`)?

**Respuesta:** Mediante `kcadm.sh get users -r <realm> -q exact=true -q username=<valor> --fields id`. El parámetro `exact=true` debe ir antes de `username` para garantizar una coincidencia exacta.

### ¿Qué es una Required Action (acción requerida) en el ciclo de vida de autenticación de un usuario?

**Respuesta:** Es una tarea de seguridad pendiente que Keycloak obliga a completar al usuario antes de otorgarle acceso a las aplicaciones (por ejemplo, verificar el correo electrónico, actualizar las credenciales o configurar MFA).

### ¿Por qué es una buena práctica delegar la administración masiva de usuarios a la API o CLI en lugar de utilizar solo la interfaz gráfica?

**Respuesta:** Porque permite automatizar de forma reproducible, reducir errores humanos en migraciones o altas masivas y facilitar la integración con sistemas corporativos externos mediante enfoques DevOps.

### ¿Qué error puede producir Keycloak 26 si intentas crear un usuario sin `firstName` ni `lastName` mediante `kcadm.sh`?

**Respuesta:** `error-user-attribute-required`. Ocurre porque el User Profile está habilitado por defecto y exige esos campos en su configuración predeterminada.

### ¿Por qué es importante utilizar `-q exact=true` al buscar un usuario por `username` en `kcadm.sh`?

**Respuesta:** Porque, sin `exact=true`, la búsqueda puede devolver coincidencias parciales (por ejemplo, `mgarcia2` al buscar `mgarcia`), lo que puede romper scripts que esperan un único UUID.
