# Módulo 4: Administración de clients y usuarios dentro de los realms

## 1. Descripción

En Keycloak, un realm funciona como una frontera lógica aislada. Dentro de ella, los dos pilares operativos fundamentales que requieren una administración precisa son los **clients** (aplicaciones, servicios o APIs que confían en Keycloak para su autenticación) y los **users** (identidades humanas o cuentas de sistema que interactúan con dichos clients).

La configuración correcta de un client determina el flujo OAuth 2.0 u OIDC permitido, las URLs de redirección válidas y el nivel de confianza criptográfico. Por su parte, la administración de usuarios define sus credenciales, atributos y asociaciones dentro de ese contexto específico.

> **Versión objetivo:** Este módulo está basado en **Keycloak 26.x**. Los comandos y comportamientos descritos son válidos para esta serie.

## 2. Objetivos

- Comprender la tipología de clients en Keycloak (**Public** vs. **Confidential**) y sus implicaciones de seguridad.
- Aprender a registrar y configurar correctamente un client y un usuario dentro de un realm específico.
- Dominar la creación automatizada de usuarios y clientes mediante la Admin CLI (`kcadm.sh`).
- Conocer cómo recuperar el `client_secret` generado por Keycloak para clientes confidential.

## 3. Desarrollo del tema y casos prácticos

### Tipología de clients en Keycloak

Al crear una aplicación en Keycloak, es crítico asignarle el tipo de acceso correcto. Según la especificación OAuth 2.0 (RFC 6749), los clientes se clasifican en dos tipos según su capacidad de mantener credenciales seguras:

1. **Public Clients (públicos):** diseñados para aplicaciones cuyo código se ejecuta en el cliente final y **no puede almacenar un secreto de forma segura**. Algunos ejemplos son las *Single Page Applications* (SPA) en React o Angular, las aplicaciones móviles y las aplicaciones de escritorio. No utilizan `client_secret` y requieren mecanismos adicionales como **PKCE** (*Proof Key for Code Exchange*) para mitigar riesgos.
2. **Confidential Clients (confidenciales):** diseñados para aplicaciones basadas en servidor (backend tradicional) capaces de **proteger de forma segura un secreto criptográfico** (`client_secret`). Este secreto se utiliza para autenticar al cliente ante Keycloak durante el intercambio de códigos por tokens.

> **Métodos de autenticación de clients:** Keycloak soporta varios métodos para que un confidential client se autentique: `client_secret_basic` (HTTP Basic Auth), `client_secret_post` (parámetros en el cuerpo), `client_secret_jwt` (JWT firmado con el secret) y `private_key_jwt` (JWT firmado con una clave privada). El método `client-secret` es el predeterminado y, según el material de origen, utiliza internamente `client_secret_post`. La elección afecta a cómo la aplicación envía sus credenciales al endpoint de tokens.

### Caso práctico: creación y configuración con la Admin CLI (`kcadm.sh`)

> **Requisito previo:** Este script presupone que ya iniciaste sesión con `kcadm.sh config credentials` (consulta el Módulo 3). Si no lo hiciste, la CLI devolverá un error de autenticación. Como alternativa, puedes usar la opción `--no-config` y pasar las credenciales en cada invocación.

El siguiente script automatiza la creación de un cliente **confidential** y un usuario dentro de un realm existente llamado `mi-realm`:

```bash
# 1. Crear un nuevo client de tipo Confidential en el realm mi-realm
/opt/keycloak/bin/kcadm.sh create clients -r mi-realm \
  -s clientId="webapp-backend" \
  -s enabled=true \
  -s publicClient=false \
  -s clientAuthenticatorType="client-secret" \
  -s 'redirectUris=["http://localhost:3000/*"]'

# 2. Crear un nuevo usuario en el mismo realm
/opt/keycloak/bin/kcadm.sh create users -r mi-realm \
  -s username="johndoe" \
  -s enabled=true \
  -s email="johndoe@example.com" \
  -s firstName="John" \
  -s lastName="Doe"

# 3. Establecer una contraseña permanente para el usuario creado
/opt/keycloak/bin/kcadm.sh set-password -r mi-realm \
  --username johndoe \
  --new-password "SecurePass123!"
```

> **Seguridad:** La contraseña del ejemplo es ilustrativa; no la reutilices. En producción, emplea credenciales únicas y almacénalas de forma segura. Además, limita las URI de redirección a los destinos necesarios y evita comodines amplios siempre que sea posible.

#### Desglose línea por línea

##### Comando 1: creación del client confidential

- `/opt/keycloak/bin/kcadm.sh create clients -r mi-realm`: crea un nuevo cliente específicamente dentro del realm `mi-realm`. El endpoint subyacente es `POST /admin/realms/mi-realm/clients`.
- `-s clientId="webapp-backend"`: define el identificador lógico con el que la aplicación se presentará ante Keycloak. Debe ser único dentro del realm.
- `-s enabled=true`: activa el cliente inmediatamente. Un cliente deshabilitado no puede solicitar tokens.
- `-s publicClient=false`: establece el cliente como confidencial; requiere autenticación con un secret.
- `-s clientAuthenticatorType="client-secret"`: especifica que el cliente se autenticará mediante un client secret. Keycloak genera automáticamente un secret al crear el cliente.
- `-s 'redirectUris=["http://localhost:3000/*"]'`: define la lista de URLs a las que Keycloak puede redirigir al usuario después de una autenticación exitosa. Es un control de seguridad importante frente a ataques de *Open Redirect*.

> **Nota sobre `protocol`:** No es necesario especificar `-s protocol="openid-connect"`, porque es el valor predeterminado para clientes nuevos. Solo debe especificarse si se quiere crear un cliente SAML.

##### Comando 2: creación del usuario

- `kcadm.sh create users -r mi-realm`: da de alta una nueva cuenta de usuario en el almacenamiento interno de Keycloak.
- `-s username="johndoe"`: establece un nombre de usuario único dentro del realm.
- `-s email="johndoe@example.com"`: define la dirección de correo electrónico, útil para notificaciones y recuperación.
- `-s firstName="John"` y `-s lastName="Doe"`: en Keycloak 26, estos campos pueden ser obligatorios debido al User Profile habilitado de forma predeterminada. Si se omiten cuando son obligatorios, el comando puede fallar con `error-user-attribute-required`.

##### Comando 3: establecimiento de contraseña

- `kcadm.sh set-password -r mi-realm`: asigna una credencial de tipo contraseña al usuario sin necesidad de utilizar la interfaz web.
- `--username johndoe`: identifica al usuario por nombre de usuario. También puede utilizarse `--userid` con el UUID.
- `--new-password "SecurePass123!"`: establece la contraseña. Si se quiere que sea temporal (para que el usuario deba cambiarla en el primer inicio de sesión), se añade `--temporary`.

### Cómo recuperar el `client_secret`

Después de crear un cliente confidential, Keycloak genera un secret que la aplicación cliente necesitará para autenticarse ante el endpoint de tokens. Para recuperarlo:

```bash
# 1. Obtener el UUID interno del cliente (no el clientId)
/opt/keycloak/bin/kcadm.sh get clients -r mi-realm \
  -q clientId=webapp-backend \
  --fields id

# 2. Usar el UUID para obtener el secret
/opt/keycloak/bin/kcadm.sh get clients/<UUID>/client-secret -r mi-realm
```

La respuesta tendrá este formato:

```json
{
  "type": "secret",
  "value": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

> **Importante:** El `client_secret` debe tratarse como una credencial sensible. Almacénalo en gestores de secretos (por ejemplo, Vault o Kubernetes Secrets) o en variables de entorno protegidas; nunca lo incluyas en el código fuente ni en repositorios Git.

## 4. Resumen

- Los clients representan las aplicaciones integradas y se clasifican en públicos (sin secret, normalmente SPA y aplicaciones móviles) y confidenciales (con secret, normalmente backends seguros).
- La creación de un cliente confidential requiere configurar `publicClient=false` y `clientAuthenticatorType=client-secret` para que Keycloak gestione un secret.
- La administración de usuarios permite definir atributos personales, estados de activación y credenciales.
- En Keycloak 26, el User Profile predeterminado puede exigir `firstName` y `lastName`; omitirlos puede producir el error `error-user-attribute-required`.
- El `client_secret` generado debe recuperarse explícitamente y almacenarse de forma segura.
- La herramienta `kcadm.sh` automatiza la gestión de clients y usuarios bajo paradigmas de infraestructura como código.

## 5. Preguntas de autoevaluación

### ¿Cuál es la diferencia arquitectónica entre un client público y uno confidencial?

**Respuesta:** Un cliente público se ejecuta en entornos donde los secretos no pueden protegerse de forma segura (como navegadores o aplicaciones móviles) y no utiliza `client_secret`. El cliente confidencial se ejecuta en servidores seguros y requiere credenciales secretas para interactuar con Keycloak.

### ¿Por qué es obligatorio configurar las Redirect URIs en un client?

**Respuesta:** Para reducir el riesgo de ataques de redirección abierta (*Open Redirect*), garantizando que Keycloak solo devuelva códigos o tokens a destinos autorizados.

### ¿Qué parámetro adicional, además de `publicClient=false`, se necesita para que Keycloak genere un `client_secret` al crear un cliente confidential?

**Respuesta:** `clientAuthenticatorType=client-secret`. Sin este parámetro, el cliente podría quedar en un estado inconsistente y el secret no generarse adecuadamente.

### ¿Cuál es el comando básico para dar de alta un usuario mediante `kcadm.sh`?

**Respuesta:** `kcadm.sh create users -r <realm> -s username=<nombre> -s enabled=true`. En Keycloak 26 también pueden requerirse `firstName` y `lastName` si el User Profile está habilitado (por defecto).

### ¿Puede un usuario pertenecer simultáneamente a dos realms diferentes compartiendo el mismo identificador interno?

**Respuesta:** No. Los usuarios están confinados al realm donde fueron creados; un mismo nombre en realms distintos corresponde a entidades independientes.

### ¿Qué acción realiza la instrucción `kcadm.sh set-password`?

**Respuesta:** Establece o actualiza la credencial de acceso del usuario en Keycloak. Sin `--temporary`, la contraseña es permanente.

### ¿Cómo se recupera el `client_secret` de un cliente confidential creado mediante la CLI?

**Respuesta:** Primero se obtiene el UUID del cliente con `kcadm.sh get clients -r <realm> -q clientId=<clientId> --fields id`. Luego se ejecuta `kcadm.sh get clients/<UUID>/client-secret -r <realm>`.

### ¿Por qué no es necesario especificar `protocol="openid-connect"` al crear un cliente OIDC?

**Respuesta:** Porque `openid-connect` es el valor predeterminado de Keycloak para clientes nuevos. Solo se especifica explícitamente si se crea un cliente SAML.
