# Módulo 1: Introducción a Keycloak como solución IAM de código abierto

## 1. Descripción

En el ecosistema de microservicios y aplicaciones web modernas, la gestión centralizada de identidades y accesos (**IAM**, *Identity and Access Management*) es un pilar crítico de la seguridad arquitectónica. Implementar lógicas de autenticación (saber quién es el usuario) y autorización (saber qué puede hacer el usuario) de forma descentralizada en cada aplicación introduce vulnerabilidades, duplicación de código y una pésima experiencia de usuario.

**Keycloak**, patrocinado por Red Hat, es una solución de código abierto robusta y basada en estándares de la industria que resuelve esta problemática. Actúa como un *Identity Provider* (IdP) centralizado que desacopla la seguridad de las aplicaciones cliente. Basado originalmente en arquitecturas Java/WildFly en versiones antiguas, Keycloak ha evolucionado hacia un núcleo moderno y optimizado impulsado por **Quarkus** (a partir de la versión 17). Esto permite un consumo de memoria reducido, un tiempo de arranque casi instantáneo y capacidades nativas para entornos en la nube (*Cloud-Native* y Kubernetes).

> **Nota sobre versiones:** Este curso está basado en **Keycloak 26.x**. Algunos comandos y variables de entorno cambiaron respecto a versiones anteriores a la 26; se indicarán las diferencias cuando aplique.

## 2. Objetivos

- Comprender el rol fundamental de Keycloak como solución IAM y su arquitectura centralizada.
- Desplegar una instancia moderna de Keycloak utilizando contenedores OCI (Docker/Podman).
- Acceder y navegar de forma segura por la Consola de Administración (Admin UI).
- Realizar la configuración inicial del entorno de desarrollo (creación del usuario administrador raíz).

## 3. Desarrollo del tema y casos prácticos

### Despliegue de Keycloak en entorno de desarrollo (Docker)

Para poner en marcha Keycloak rápidamente en un entorno local con fines de prueba y desarrollo, utilizaremos la imagen oficial de Quay.io basada en Quarkus y el modo de desarrollo (`start-dev`).

Ejecuta el siguiente comando en tu terminal:

```bash
docker run -d \
  --name keycloak-dev \
  -p 127.0.0.1:8084:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.7.4 \
  start-dev \
  --http-relative-path=/auth0 \
  --hostname=https://key00.planeta0.com/auth0 \
  --proxy-headers=xforwarded
```

El mapeo 127.0.0.1:8084:8080 significa que Apache podrá acceder al contenedor por el puerto 8084 del servidor y Keycloak seguirá escuchando internamente en el 8080.

Comprueba que está levantado:
```
docker ps
```

Y que responde localmente (para esto espera un par de minutos:
```
curl -I http://127.0.0.1:8084/auth0/
```

> **Cambio importante en Keycloak 26+:** Las variables `KEYCLOAK_ADMIN` y `KEYCLOAK_ADMIN_PASSWORD` fueron deprecadas en Keycloak 26.0. Debes usar `KC_BOOTSTRAP_ADMIN_USERNAME` y `KC_BOOTSTRAP_ADMIN_PASSWORD`. Si utilizas las variables antiguas en Keycloak 26+, verás una advertencia en los logs y eventualmente dejarán de funcionar.

> **Comportamiento del administrador inicial:** Las credenciales de administrador definidas mediante estas variables solo se crean en el primer arranque, cuando la base de datos (el realm `master`) está vacía. En arranques posteriores del mismo contenedor, estas variables se ignoran. Si pierdes el acceso de administrador, deberás usar el comando `kc.sh bootstrap-admin user`.

#### Desglose de los parámetros

- `docker run -d`: ejecuta un nuevo contenedor en segundo plano (*detached mode*).
- `--name keycloak-dev`: asigna un nombre descriptivo y fácil de referenciar al contenedor.
- `-p 8080:8080`: mapea el puerto 8080 del contenedor (puerto predeterminado de Keycloak en Quarkus) al puerto 8080 de la máquina anfitriona.
- `-e KC_BOOTSTRAP_ADMIN_USERNAME=admin`: define el nombre de usuario del administrador inicial (Keycloak 26+).
- `-e KC_BOOTSTRAP_ADMIN_PASSWORD=admin`: define la contraseña del administrador inicial. **Nota de seguridad:** nunca utilices credenciales genéricas como `admin/admin` en entornos de producción.
- `quay.io/keycloak/keycloak:26.7.4`: especifica la imagen oficial de Keycloak. Se fija la versión para garantizar la reproducibilidad, en lugar de usar `:latest`.
- `start-dev`: inicia Keycloak en modo de desarrollo. Configura automáticamente una base de datos H2 embebida (en modo archivo dentro del contenedor) y habilita funciones útiles para desarrollo, como HTTP sin exigir certificados TLS de inmediato.

Una vez iniciado el contenedor:

1. Abre el navegador y navega a [http://localhost:8080](http://localhost:8080).
2. En la página de bienvenida, haz clic en **Administration Console**.
3. Introduce las credenciales configuradas (`admin` / `admin`).

### Recomendaciones de producción y hardening

- **Modo de producción:** El comando `start-dev` nunca debe usarse en entornos productivos. En producción se debe utilizar `kc.sh start`, configurar una base de datos externa persistente (por ejemplo, PostgreSQL) y habilitar TLS/HTTPS de forma obligatoria.
- **Gestión de secretos:** Las contraseñas de administración deben gestionarse mediante mecanismos seguros (Docker Secrets, Kubernetes Secrets o HashiCorp Vault), en lugar de exponerse en texto plano en scripts de shell.
- **Versión de la imagen:** Fija siempre una versión específica (por ejemplo, `26.7.4`) en lugar de usar `:latest`. Esto permite despliegues reproducibles y controlar cuándo actualizar.

## 4. Resumen

- Keycloak centraliza la autenticación y autorización, evitando que las aplicaciones manejen directamente las credenciales de usuario.
- Las versiones modernas basadas en Quarkus ofrecen un rendimiento superior y un despliegue ágil mediante contenedores.
- El comando `start-dev` es ideal para pruebas locales: configura automáticamente el acceso inicial y una base de datos H2 embebida. Los datos se pierden al eliminar el contenedor, pero persisten mientras este exista.
- En Keycloak 26+, las variables para el administrador inicial son `KC_BOOTSTRAP_ADMIN_USERNAME` y `KC_BOOTSTRAP_ADMIN_PASSWORD`; las antiguas `KEYCLOAK_ADMIN*` están deprecadas.

## 5. Preguntas de autoevaluación

### ¿Cuál es el propósito principal de Keycloak dentro de una arquitectura empresarial moderna?

**Respuesta:** Funcionar como una solución centralizada de Gestión de Identidades y Accesos (IAM) para manejar la autenticación y autorización de usuarios en múltiples aplicaciones y servicios de forma estandarizada.

### ¿Qué motor tecnológico subyace en las versiones modernas de Keycloak (a partir de la versión 17)?

**Respuesta:** Quarkus, que permite un rendimiento optimizado, menor consumo de memoria y tiempos de arranque reducidos, orientados a entornos *Cloud-Native*.

### ¿Para qué sirve el parámetro `start-dev` al iniciar el contenedor Docker de Keycloak?

**Respuesta:** Inicia Keycloak en modo desarrollo, configura automáticamente una base de datos H2 embebida y permite conexiones HTTP sin cifrado TLS estricto.

### ¿Por qué se considera una mala práctica de seguridad utilizar `start-dev` en producción?

**Respuesta:** Porque utiliza una base de datos embebida (H2) que no garantiza la persistencia ante la eliminación del contenedor y omite requisitos críticos de seguridad, como el cifrado obligatorio en tránsito (TLS).

### ¿Qué variables de entorno se utilizan en Keycloak 26+ para configurar el administrador inicial en un contenedor?

**Respuesta:** `KC_BOOTSTRAP_ADMIN_USERNAME` y `KC_BOOTSTRAP_ADMIN_PASSWORD`. Las antiguas `KEYCLOAK_ADMIN` y `KEYCLOAK_ADMIN_PASSWORD` están deprecadas desde Keycloak 26.

### ¿A qué puerto mapea por defecto Keycloak (Quarkus) en su contenedor OCI?

**Respuesta:** Al puerto `8080`.
